## 当前实现与启用

`CanalClient` 将 bullet/comment/video 的 INSERT、UPDATE、DELETE 对应视频写入业务库 `feedback_vector_work` 后才允许 ACK。队列按视频合并，generation 标识新变化；新事件等待至少 2 秒后领取，使按整秒截取的快照覆盖刚落库的反馈。持久租约 20 分钟，失败 60 秒后重试，最多连续尝试 10 次，失败保留 last_error，可通过人工重置 attempts/next_at 重放。新增事件也会重置失败计数。已经完成的行继续保留用于合并；旧租约不能完成新领取的工作。

`FeedbackWarmWorker` 使用专用单线程调度器，通过私有服务身份领取任务、流式读取权威快照、每 16 条调用 `FeedbackCompression.warm`。后者复用报告的清洗、Reference、Namespace 和 encode；已存在向量不重复请求。每次视频扫描最多 20000 条、64 MiB，单行 256 KiB，默认处理 600 秒和最多 1500 次 embedding 调用，超限保留重试/失败状态，报告按需兜底。全视频扫描覆盖父评论变化和点赞导致的代表选择变化；不是维护常驻聚类，聚类仍按报告范围执行。暂不物理删除旧向量；旧版本和已删除记录必须由报告授权快照排除，后续保留清理独立治理。

先应用 `deploy/site/migrations/20261108_feedback_vector_work.sql`，创建独立 2560 维集合，生成至少 32 字节的随机私有 `feedback-warm-token`，再叠加 `compose.feedback-vector.yaml` 和 `compose.feedback-warm.yaml`。服务密钥只用于私有 `/internal/agent/vector-work/*`，现有 Nginx 必须继续拦截公网 internal 路由。两端使用相同 secret；模型维数与集合须一致。默认不开启；修改后重启生效。该 overlay 使用现有 agent 与 business 共享网络命名空间的站点部署方式。

历史回填可在独立运维批次执行 `INSERT INTO feedback_vector_work(video_id,next_at) SELECT video_id,UTC_TIMESTAMP(6) FROM video WHERE is_delete=0 ON DUPLICATE KEY UPDATE generation=generation+1,attempts=0,next_at=UTC_TIMESTAMP(6)`；须结合存量规模、供应商限流和部署内存分段受控执行。当前没有自动启动全库回填。

## 契约

Canal 只观察已提交的 `bullet`、`comment` 行变化；它不是可丢弃的异步线程。消费者须在确认 Canal 批次之前，把来源、记录标识、视频标识和事件版本可靠写入持久队列；重复投递可重放。不得把完整反馈或凭据写入日志。向量任务失败不能回滚已提交的发送，也不能影响既有弹幕 Redis 更新。

后台工作者以有界并发和批量消费队列，失败按可配置退避重试，超过上限保留可观察、可重放的失败记录；进程中断后租约到期可恢复。领取与完成必须以版本和租约栅栏核对，防止较老事件覆盖较新事件或误确认。服务间调用必须使用独立的服务身份和私网访问控制，不能冒充用户会话或使用长期登录令牌。

每次处理时从权威业务数据重读当前行、视频所有者和必要回复上下文，复用报告快照的脱敏、时间转换、作者判断及清洗逻辑，生成与报告完全相同的 Unit 和 Reference。目标命名空间包含租户、视频作者、视频、来源和模型版本。报告仍先做实时授权并与本次授权快照的精确版本取交集；向量命中从不构成读权限。父评论变化、删除和视频删除必须使受影响的旧版本不可作为当前证据；旧引用按明确保留策略清理。缺失或短文本遵循与报告相同的过滤规则。

新模型或维度使用独立集合及命名空间。2560 维集合必须预先建立、验证索引和权限，不能把旧维向量写入新集合。冷启动历史回填与新增事件分开、有界限速；优先处理新增事件。报告等待时若预处理尚未完成，继续使用现有按需生成和授权快照，不依赖预热成功。

验收必须覆盖事务回滚无事件、提交后消费、重复投递、工作者崩溃恢复、更新删除竞态、回复上下文变化、限流/认证错误、模型版本变更、授权撤销、报告缓存命中与隔离、少量及空反馈，最后用真实评论和弹幕端到端检查任务状态和 Trace。只在完成测试和发布后将状态改为已实现。
